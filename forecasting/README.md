# Prophet Workload Forecasting Module

This directory provides the time-series forecasting component for **Predictive Autoscaling in Kubernetes using Load Forecasting**. It uses Facebook Prophet to fit historical Kubernetes workload traffic patterns and project expected load into future time horizons.

---

## 1. Overview and Architecture

Standard Kubernetes Horizontal Pod Autoscaler (HPA) operates reactively: it measures resource consumption (such as CPU or current request rates) after load arrives, introducing delay while metrics propagate and pods spin up.

This module models historical request rates and forecasts traffic trends ahead of time so proactive scaling decisions (e.g., via KEDA) can provision capacity before latency spikes or SLO violations occur.

### Core Files
- [`forecast.py`](file:///c:/Users/dhanu/Desktop/predictive-k8s-autoscaling/forecasting/forecast.py): Loads collected experiment metrics, cleans and converts timestamps to Prophet's `ds` and `y` format, validates data integrity, fits a Prophet regression model, and generates future load projections with prediction intervals (`yhat`, `yhat_lower`, `yhat_upper`).
- [`evaluate_forecast.py`](file:///c:/Users/dhanu/Desktop/predictive-k8s-autoscaling/forecasting/evaluate_forecast.py): Evaluates forecast accuracy strictly against held-out observations using chronological splitting (preventing data leakage) and calculates Mean Absolute Error (MAE) and Root Mean Squared Error (RMSE).
- [`requirements.txt`](file:///c:/Users/dhanu/Desktop/predictive-k8s-autoscaling/forecasting/requirements.txt): Python dependencies for Prophet, Pandas, NumPy, and Scikit-learn.

## 2. Experimental Data Format

The module consumes CSV datasets generated by the experiment metrics collector ([`experiments/collect_metrics.py`](file:///c:/Users/dhanu/Desktop/predictive-k8s-autoscaling/experiments/collect_metrics.py)):

- **Timestamp Column**: `timestamp_utc` (ISO-8601 UTC string, e.g. `2026-10-29T10:21:57.754010+00:00`). Converted to timezone-naive UTC for Prophet's `ds` column.
- **Request Rate Column**: `http_work_rps` (Prometheus 1m per-second request rate specifically on `GET /api/work`). Mapped to Prophet's target `y` column.

All five experimental CSV files in `experiments/` share this identical 19-column schema:
`timestamp_utc`, `epoch_timestamp`, `collection_status`, `cpu_usage_cores`, `memory_working_set_bytes`, `memory_working_set_mb`, `pod_count`, `deployment_replicas`, `deployment_available_replicas`, `hpa_current_replicas`, `hpa_desired_replicas`, `http_requests_total`, `http_requests_work_total`, `http_rps`, `http_work_rps`, `http_error_rps`, `latency_p50_seconds`, `latency_p95_seconds`, `latency_p99_seconds`.

## 4. Usage Commands (PowerShell)

### A. Training & Generating Forecasts (`forecast.py`)

Train Prophet on historical data and generate a 15-step forecast into the future:

```powershell
# Forecast using the periodic workload profile
python forecasting/forecast.py --input-csv experiments/hpa_periodic.csv --output-csv forecasting/forecast_periodic.csv --horizon 15

# Forecast stable workload profile with 100% training data
python forecasting/forecast.py --input-csv experiments/hpa_stable.csv --output-csv forecasting/forecast_stable.csv --horizon 20 --test-size 0.0
```

#### Command-Line Arguments
- `--input-csv`: Path to the input experiment CSV (required).
- `--output-csv`: Destination CSV path for forecasted points (default: `forecasting/forecast_output.csv`).
- `--horizon`: Number of future time steps to project ahead (default: `15`).
- `--metric`: Target column to forecast (default: `http_work_rps`).
- `--timestamp-col`: Timestamp column name (default: `timestamp_utc`).
- `--test-size`: Proportion of data held out (default: `0.2`).
- `--seed`: Random seed for reproducibility (default: `42`).

#### Forecast Output Schema
The generated CSV contains:
- `ds`: Forecast timestamp (UTC).
- `yhat`: Predicted request rate (RPS), constrained to $\ge 0$.
- `yhat_lower`: Lower bound of the 95% uncertainty interval.
- `yhat_upper`: Upper bound of the 95% uncertainty interval.

---

### B. Evaluating Forecast Accuracy (`evaluate_forecast.py`)

Evaluate model predictions against held-out actual measurements:

```powershell
# Evaluate on the periodic profile (recommended first run)
python forecasting/evaluate_forecast.py --input-csv experiments/hpa_periodic.csv --test-size 0.25

# Evaluate and save aligned actuals vs predicted to CSV
python forecasting/evaluate_forecast.py --input-csv experiments/hpa_periodic.csv --test-size 0.25 --output-csv forecasting/eval_periodic.csv

# Output summary as JSON for automated pipelines
python forecasting/evaluate_forecast.py --input-csv experiments/hpa_periodic.csv --test-size 0.25 --json
```

#### Evaluation Metrics
- **MAE (Mean Absolute Error)**: $\frac{1}{N} \sum_{i=1}^N |y_i - \hat{y}_i|$ (average magnitude of forecast error in RPS).
- **RMSE (Root Mean Squared Error)**: $\sqrt{\frac{1}{N} \sum_{i=1}^N (y_i - \hat{y}_i)^2}$ (penalizes large forecast spikes or timing errors).
- **NRMSE (Normalized RMSE)**: $\frac{\text{RMSE}}{\bar{y}}$ (relative forecast error normalized by mean observed request rate).

## 5. Which Real CSV to Use First and Why

**Recommended First Dataset**: `experiments/hpa_periodic.csv`

### Rationale:
1. **Dynamic Variation**: Unlike `hpa_stable.csv` (which hovers around a static user concurrency with little trend or variation), `hpa_periodic.csv` alternates between low load (~2 users) and high load (~10 users). This exhibits clear changepoints and cyclical shifts.
2. **Train/Test Contrast**: In periodic data, held-out evaluation genuinely tests whether the model captures trend direction rather than trivial constant-value matching.
3. **Autoscaling Relevance**: Predictive autoscaling provides maximum advantage over reactive HPA on cyclic or recurring workloads by anticipating the upcoming transition between low and high traffic phases.

## 6. Assumptions and Limitations

1. **Short Observation Duration**:
   Current experimental CSVs contain 61 snapshots recorded at ~2-second intervals (~122 seconds total). Prophet is traditionally designed for daily, weekly, or yearly seasonality over months of data. On sub-minute scales, Prophet operates primarily as a trend changepoint detector and linear extrapolator rather than learning sub-minute Fourier periodicities.
2. **Frequency and Jitter**:
   Prometheus collector polls every ~2.0 seconds with small network jitter ($\pm 1\,\text{ms}$). The pipeline computes the median time delta (`2s`) to generate future intervals and uses nearest-neighbor alignment (`merge_asof`) within a 2.5-second tolerance for evaluation.
3. **Non-Negativity Constraint**:
   Raw Prophet Gaussian likelihood models can occasionally project negative values for series near zero. The module explicitly clamps `yhat`, `yhat_lower`, and `yhat_upper` to $\ge 0.0$ since negative HTTP request rates are physically impossible.
4. **Prometheus Rate Smoothing**:
   Prometheus rates are computed over a 1-minute window (`[1m]`). Sudden bursts and step transitions in traffic appear as gradual ramp-ups and ramp-downs in `http_work_rps`, which the forecaster models accordingly.
